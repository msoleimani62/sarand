# ساختار مخزن (`--structure`)

وضعیت: **R14-A1 پیاده‌سازی شده است**: ماژول‌ها، importها، طبقه‌بندی importها و
چرخه‌ها. نمادها و فراخوانی‌ها، entry pointها و شناسه‌ی ساختاری پایدار **هنوز
پیاده‌سازی نشده‌اند** (R14-A2 و R14-A3، به `docs/R14A_PLAN.md` نگاه کنید).

`sarand --structure` سورس پایتون پروژه را با ماژول استاندارد `ast` می‌خواند و ساختار
را به گزارش اضافه می‌کند. هرگز کد مخزن را اجرا نمی‌کند و فقط فایل‌هایی را می‌خواند که
گزارش اجازه‌ی خواندنشان را دارد (نه فایل علامت‌خورده به‌عنوان راز، نه فایل بزرگ‌تر از
حد اندازه؛ چنین فایلی با `skipped_size` فهرست می‌شود، نه حذف). به‌طور پیش‌فرض خاموش
است و گزارش پیش‌فرض تغییر نمی‌کند.

## چهار چیزی که جدا می‌مانند

| چیز | از کجا می‌آید | سرند با آن چه می‌کند |
|---|---|---|
| وابستگی **اعلام‌شده** | `pyproject.toml`، `requirements.txt` | به‌عنوان شاهد روی بسته‌ی بیرونی ثبت می‌شود؛ خودش هرگز import نیست |
| بسته‌ی **نصب‌شده** | محیط | هرگز خوانده نمی‌شود |
| import **یافت‌شده در سورس** | دستور `import` و فراخوانی `importlib`/`__import__` | یک یال |
| رابطه‌ی **حل‌شده‌ی** مخزن | یالی که هدفش ماژول مخزن است | گراف import و چرخه‌ها |

## import به چه چیزی حل می‌شود (`target_class`)

| کلاس | معنا |
|---|---|
| `internal` | یک ماژول همین مخزن (یا بسته‌ی namespace ضمنی) |
| `stdlib` | نام کتابخانه‌ی استاندارد؛ فهرست همان `sys.stdlib_module_names` مفسری است که سرند را اجرا کرده و در `meta` ثبت می‌شود |
| `external_declared` | ماژول مخزن نیست و نام نرمال‌شده‌اش با یک وابستگی اعلام‌شده برابر است |
| `external_unmatched` | ماژول مخزن نیست، stdlib نیست، و اعلانی ندارد. نام import با نام توزیع می‌تواند فرق کند (`yaml` و `pyyaml`) و سرند metadata نصب‌شده را نمی‌خواند، پس حدس نمی‌زند؛ این همان فهرست «بیرونیِ حل‌نشده» است |
| `internal_unresolved` | نام از یک بسته‌ی مخزن شروع می‌شود ولی هدفی پیدا نشد: زیرماژول گم‌شده، نام مبهم (چند ماژول جور است)، import نسبی فراتر از بسته‌ی بالا |
| `dynamic` | نام ماژول در زمان اجرا محاسبه می‌شود (`importlib.import_module(name)`) |

## اعتماد (confidence)

فقط با این قواعد داده می‌شود. شرطی‌بودن import یک **پرچم** است، نه سطح اعتماد.

| سطح | قاعده | مثال‌ها |
|---|---|---|
| `definite` | نام با قواعد خود پایتون دقیقاً به یک ماژول مخزن (یا نام stdlib یا اعلام‌شده) متصل می‌شود | `import a.b` وقتی `a/b.py` هست؛ import نسبی که روی یک فایل می‌نشیند؛ نام stdlib؛ نامی برابر با یک اعلان |
| `probable` | یک نامزد هست ولی یک فرض لازم بود | همان نام ماژول در دو ریشه هست و ریشه‌ی خود import‌کننده ترجیح داده شد؛ ماژول مخزن نام stdlib را سایه می‌زند؛ `importlib.import_module("literal")`؛ بسته‌ی بیرونی که فقط با حذف مطابقت یافته |
| `unknown` | شاهد نمی‌تواند هدف را نام ببرد | نام ماژول محاسبه‌شده؛ نام مبهم؛ زیرماژول گم‌شده؛ import نسبی بدون بسته‌ی والد |

یال `unknown` هرگز وابستگی نیست: هرگز چرخه نمی‌سازد.

## پرچم‌های import

`conditional` (داخل `if` یا `try` ای که `ImportError` را می‌گیرد)، `type_only` (زیر
`if TYPE_CHECKING:`)، `lazy` (داخل بدنه‌ی تابع)، `relative`، `star`. دکوراتورها و
مقدارهای پیش‌فرض هنگام تعریف تابع اجرا می‌شوند، پس lazy نیستند.

## ریشه‌های سورس و نام ماژول

نام ماژول از یک ریشه‌ی سورس شروع می‌شود: ریشه‌ی اعلام‌شده در `pyproject.toml` (maturin
`python-source`، setuptools `package-dir` و `packages.find.where`) که فایل را در بر
بگیرد، وگرنه نزدیک‌ترین پوشه‌ی بالادست بدون `__init__.py`. نامی که در دو ریشه هست فقط
وقتی حل می‌شود که ریشه‌ی خود import‌کننده دقیقاً یکی از آن‌ها را داشته باشد (probable)؛
وگرنه `internal_unresolved` است. پوشه‌ای بدون `__init__.py` میان ریشه و ماژول، بسته‌ی
namespace ضمنی است.

راه‌اندازی بسته‌ی والد (`import a.b.c` ابتدا `a/__init__.py` را اجرا می‌کند) به‌عنوان یال
**مدل نمی‌شود**: هر بسته و زیرماژول‌هایش را چرخه می‌کرد. `from pkg import name` فقط وقتی
به `pkg` وابسته است که `name` زیرماژول مخزن نباشد.

## چرخه‌ها

مؤلفه‌های قویاً همبند گراف import مخزن، بدون بازگشت، به‌اضافه‌ی ماژولی که خودش را
import می‌کند. چرخه **eager** است وقتی پس از حذف importهای `type_only` و `lazy` هنوز
بماند، یعنی بتواند هنگام import شکست بخورد؛ وگرنه «lazy or type-only» فهرست می‌شود.

## منشأ تجزیه و محدودیت‌ها

هر فایل منشأ دارد: parser (`python-ast`)، نسخه‌ی مفسر، کامل‌بودن (`full`، `partial`،
`failed`، `skipped_size`) و کدهای محدودیت: `syntax_error`،
`unsupported_syntax_for_interpreter`، `encoding_error`، `recursion_limit`، `node_cap`،
`too_large`، `unreadable`، `dynamic_construct_seen`. فایلی که خوانده نشود با دلیل و مکان
خطا در خروجی می‌ماند، پس فایل خراب هرگز صفر بی‌صدا نیست.

**«شناسایی نشد» یعنی «وجود ندارد» نیست.** importهای پویا، `getattr`/`setattr`،
monkey-patching، بارگذاری پلاگین با entry-point و کد تولیدشده می‌توانند رابطه‌هایی بسازند
که خواندن ایستا نمی‌بیند. `dynamic_construct_seen` یعنی فایل چنین ساختاری دارد.

دو ورودی محیطی در `meta` نام برده می‌شوند و پنهان نیستند: نسخه‌ی مفسر (دستور زبان `ast`
و فهرست stdlib به آن بستگی دارند، پس فایل با نحو جدیدتر روی مفسر قدیمی‌تر `failed` است) و
منبع فهرست stdlib.

## کجا دیده می‌شود

- **JSON** (`structure`، شمای ۱٫۷): همه‌چیز، از جمله هر یال با شاهد و مکانش. به
  `docs/JSON_SCHEMA.fa.md` نگاه کنید.
- **Markdown و HTML**: شمارش‌ها، چرخه‌های import (۱۰ مورد اول)، importهای حل‌نشده (۲۰ مورد
  اول) و بسته‌های بیرونی import‌شده (۳۰ مورد اول)؛ جمع کل همیشه نشان داده می‌شود و آنچه
  بریده شده می‌گوید چند مورد نشان داده نشده.
- **Text**: یک خط.
- **SARIF**: شامل نمی‌شود.

همه‌ی شمارش‌ها از یک جا می‌آیند (`structure/serialize.py` و `core/report_views.py`)، پس
قالب‌ها هم‌نظرند.

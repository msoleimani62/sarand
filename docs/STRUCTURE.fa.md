# ساختار مخزن (`--structure`)

وضعیت: **R14-A1 و R14-A2 و R14-A3 پیاده‌سازی شده‌اند**: ماژول‌ها، importها، طبقه‌بندی importها،
چرخه‌ها، نمادها، روابط بین نمادها، entry pointها، بصمت محتوای نسخه‌دار و کلاس‌های تطبیق بین دو حالت،
ارزیابی‌شده روی دو مخزن واقعی (`docs/R14A_GATE_REPORT.md`). استفاده از شناسه برای مقایسه‌ی دو اجرا (baseline)
کار R14-D است و **هنوز پیاده‌سازی نشده**؛ زبان‌های دیگر شروع نشده‌اند.

`sarand --structure` سورس پایتون پروژه را با ماژول استاندارد `ast` می‌خواند و ساختار
را به گزارش اضافه می‌کند. هرگز کد مخزن را اجرا نمی‌کند و فقط فایل‌هایی را می‌خواند که
گزارش اجازه‌ی خواندنشان را دارد (نه فایل علامت‌خورده به‌عنوان راز، نه فایل بزرگ‌تر از
حد اندازه؛ چنین فایلی با `skipped_size` فهرست می‌شود، نه حذف). به‌طور پیش‌فرض خاموش
است و گزارش پیش‌فرض تغییر نمی‌کند.

## چهار چیزی که جدا می‌مانند

| چیز | از کجا می‌آید | سرند با آن چه می‌کند |
|---|---|---|
| وابستگی **اعلام‌شده** | `pyproject.toml` (همه‌ی بخش‌های فهرست‌شده در «وابستگی‌های اعلام‌شده»)، `requirements.txt` | به‌عنوان شاهد، همراه با بخش، روی بسته‌ی بیرونی ثبت می‌شود؛ خودش هرگز import نیست |
| بسته‌ی **نصب‌شده** | محیط | هرگز خوانده نمی‌شود |
| import **یافت‌شده در سورس** | دستور `import` و فراخوانی `importlib`/`__import__` | یک یال |
| رابطه‌ی **حل‌شده‌ی** مخزن | یالی که هدفش ماژول مخزن است | گراف import و چرخه‌ها |

## import به چه چیزی حل می‌شود (`target_class`)

| کلاس | معنا |
|---|---|
| `internal` | یک ماژول همین مخزن (یا بسته‌ی namespace ضمنی) |
| `stdlib` | نام کتابخانه‌ی استاندارد؛ فهرست همان `sys.stdlib_module_names` مفسری است که سرند را اجرا کرده و در `meta` ثبت می‌شود |
| `external_declared` | ماژول مخزن و stdlib نیست و یک manifest توزیعی را اعلام می‌کند که این import را عرضه می‌کند: توزیعی با همان نام نرمال‌شده (`definite`) یا توزیعی که جدول `sarand/structure/distributions.py` می‌گوید نام import را عرضه می‌کند (`probable`). `declared_in` همه‌ی اعلام‌ها را با بخششان فهرست می‌کند |
| `external_unmatched` | ماژول مخزن و stdlib نیست و هیچ اعلامی که سرند می‌خواند آن را عرضه نمی‌کند. این همان فهرست «بیرونیِ حل‌نشده» است: یعنی *هیچ اعلام خواندنی جور نشد*، که با *اعلام‌نشده* یکی نیست (آنچه خوانده نمی‌شود در «وابستگی‌های اعلام‌شده» آمده) |
| `internal_unresolved` | نام از یک بسته‌ی مخزن شروع می‌شود ولی هدفی پیدا نشد: زیرماژول گم‌شده، نام مبهم (چند ماژول جور است)، import نسبی فراتر از بسته‌ی بالا |
| `dynamic` | نام ماژول در زمان اجرا محاسبه می‌شود (`importlib.import_module(name)`) |

## وابستگی‌های اعلام‌شده

import بیرونی با آنچه manifestهای پروژه **اعلام** می‌کنند سنجیده می‌شود. پنج اصطلاح جدا نگه داشته می‌شوند:

| اصطلاح | معنا |
|---|---|
| **نام import** | نام سطح‌بالایی که در سورس نوشته شده: `yaml`، `PIL`، `pytest` |
| **نام distribution** | نامی که manifest برای بسته به کار می‌برد: `PyYAML`، `Pillow`، `pytest`؛ بعد از نرمال‌سازی PEP 503 مقایسه می‌شود (حروف کوچک، دنباله‌ی `-` و `_` و `.` یک `-` می‌شود) |
| **اعلام وابستگی** | یک نام distribution در یک بخش از یک manifest |
| **بخش** | جایی که manifest آن را فهرست کرده؛ نام گروه وابستگی (`tests`، `docs`، ...) یا extra جزو برچسب است |
| `external_declared` / `external_unmatched` | دست‌کم یک اعلام خواندنی این import را عرضه می‌کند / هیچ‌کدام نمی‌کند |

**آنچه خوانده می‌شود** (پایتون، در هر پوشه‌ای که manifest دارد). برچسب `declared_in` به شکل
`<پوشه>/pyproject.toml#<بخش>` یا `<پوشه>/requirements.txt` است:

| برچسب بخش | منبع |
|---|---|
| `project.dependencies` | وابستگی‌های اجرایی PEP 621 |
| `project.optional-dependencies.<extra>` | extraهای PEP 621 |
| `dependency-groups.<group>` | گروه‌های PEP 735 (ورودی `{include-group = ...}` بسته نیست و رد می‌شود) |
| `build-system.requires` | نیازهای ساخت |
| `tool.poetry.dependencies`، `tool.poetry.dev-dependencies`، `tool.poetry.group.<group>.dependencies` | Poetry (`python` قید مفسر است، نه بسته) |
| `requirements.txt` | هر خط یک نیازمندی؛ گزینه‌ها و کامنت‌ها رد می‌شوند |

**تطبیق.** ابتدا distribution با همان نام نرمال‌شده‌ی import امتحان می‌شود (`definite`). نام import می‌تواند با
نام distribution فرق کند، پس یک **جدول صریح** و کوتاه (`sarand/structure/distributions.py`) برای چند نام import
جاافتاده همه‌ی distributionهایی را که آن را عرضه می‌کنند فهرست می‌کند (`yaml` را `pyyaml` عرضه می‌کند،
`PIL` را `pillow` و `pillow-simd`، `cv2` را چهار distribution از `opencv-*`). اگر هر کدام اعلام شده باشد، import
`external_declared` با اعتماد `probable` است (جفت از جدول می‌آید، نه از متن پروژه)، روش حل
`declared-distribution`، و `declared_in` همه‌ی اعلام‌های یافت‌شده را فهرست می‌کند. نامی که در جدول نیست
از روی شباهت حدس زده نمی‌شود و `external_unmatched` می‌ماند؛ جدول کامل نیست.

**آنچه خوانده نمی‌شود:** بسته‌های نصب‌شده (هرگز؛ `top_level.txt` هم نه)، `setup.py`، `setup.cfg`، `Pipfile`،
گونه‌های `requirements-*.txt`، جدول‌های `uv` و `pdm` و `hatch`، و manifestهای Cargo و npm برای importهای
پایتون. بسته‌ای که فقط آنجا اعلام شده `external_unmatched` است.

**دامنه.** اعلام در هر جای پروژه‌ی اسکن‌شده برای کل پروژه حساب می‌شود؛ به پوشه‌ی manifestش محدود نیست. اسکریپت
ارزیابی می‌گوید چند یال اعلام‌شده manifest اعلام‌کننده‌ای بالاتر از فایل import‌کننده ندارند
(`scripts/structure_eval_imports.py --audit-external`).

## اعتماد (confidence)

فقط با این قواعد داده می‌شود. شرطی‌بودن import یک **پرچم** است، نه سطح اعتماد.

| سطح | قاعده | مثال‌ها |
|---|---|---|
| `definite` | نام با قواعد خود پایتون دقیقاً به یک ماژول مخزن (یا نام stdlib یا اعلام‌شده) متصل می‌شود | `import a.b` وقتی `a/b.py` هست؛ import نسبی که روی یک فایل می‌نشیند؛ نام stdlib؛ نامی برابر با یک اعلان |
| `probable` | یک نامزد هست ولی یک فرض لازم بود | همان نام ماژول در دو ریشه هست و ریشه‌ی خود import‌کننده ترجیح داده شد؛ ماژول مخزن نام stdlib را سایه می‌زند؛ `importlib.import_module("literal")`؛ بسته‌ی بیرونی که فقط با حذف مطابقت یافته؛ بسته‌ی بیرونی که فقط از راه distributionای اعلام شده که نام import را عرضه می‌کند (`import yaml` با `PyYAML` اعلام‌شده) |
| `unknown` | شاهد نمی‌تواند هدف را نام ببرد | نام ماژول محاسبه‌شده؛ نام مبهم؛ زیرماژول گم‌شده؛ import نسبی بدون بسته‌ی والد |

یال `unknown` هرگز وابستگی نیست: هرگز چرخه نمی‌سازد.

## پرچم‌های import

`conditional`، `type_only`، `lazy`، `relative`، `star`.

- **`conditional`**: وقتی scope اجرا می‌شود ممکن است این import اجرا نشود. برای شاخه‌های
  `if`/`elif`/`else`؛ بدنه‌ی `try` ای که handler ی `ImportError` از آن محافظت می‌کند؛ هر handler ی
  `except`؛ `else` ی `try`؛ بدنه و `else` ی `for` و `while`؛ caseهای `match`؛ سمت راست
  `and`/`or`؛ شاخه‌های عبارت شرطی؛ بدنه‌ی comprehension تنظیم می‌شود. برای `finally` یا `with`
  **تنظیم نمی‌شود** (context manager می‌تواند exception را ببلعد، ولی سرند آن را تعیین
  نمی‌کند). `try` بدون handler ی `ImportError` بدنه‌اش را شرطی نمی‌کند.
- **`type_only`**: زیر `if TYPE_CHECKING:` (و `else` ی `if not TYPE_CHECKING:`)؛ همیشه
  `conditional` هم هست.
- **`lazy`**: داخل بدنه‌ی تابع یا lambda، یعنی import هنگام فراخوانی تابع اجرا می‌شود.
  دکوراتور، مقدار پیش‌فرض و annotation هنگام تعریف اجرا می‌شوند، پس lazy نیستند.
- **`relative`**: شکل `from . import x`. **`star`**: `from m import *`.

یک handler از import **محافظت می‌کند** وقتی `ImportError`، `ModuleNotFoundError`، `Exception` یا
`BaseException` را نام ببرد (یا اصلاً نوع نداشته باشد)، به‌صورت نام متصل به builtin، یا
`builtins.<name>`، یا alias ای که از builtin گرفته شده (`IE = ImportError`)، یا داخل tuple
از این‌ها. `foo.ImportError` و `ImportError` ی که دوباره مقدار گرفته حساب نمی‌شوند.

## شکل‌های شناخته‌شده و حدشان

نام‌ها **بر اساس scope** حل می‌شوند، نه بر اساس املا. جدول انقیاد فقط `TYPE_CHECKING`،
ماژول‌های `typing`/`typing_extensions`، `importlib` و `builtins` (زیر هر alias)،
`importlib.import_module`، `importlib.__import__`، `__import__` و خانواده‌ی `ImportError` را
می‌شناسد. نامی که به چیز دیگری دوباره متصل شود، یا در یک scope به دو شکل متفاوت متصل باشد،
مبهم است و شناخته نمی‌شود. پشتیبانی‌شده:

- sentinel ی `TYPE_CHECKING` به شکل `from typing import TYPE_CHECKING [as T]`،
  `typing.TYPE_CHECKING` (همچنین با `import typing as t`) و ترفند `TYPE_CHECKING = False`.
  نامی با همین املا که از جای دیگر بیاید (`from .compat import TYPE_CHECKING`،
  `custom.TYPE_CHECKING`، پارامتر، متغیر) فقط `conditional` است.
- `importlib.import_module(name, package=None)` و `__import__(name, globals, locals, fromlist,
  level)` ی builtin، با نام خودشان یا با alias (`import importlib as il`،
  `from importlib import import_module as im`، `from builtins import __import__ as ci`). نام
  literal مثل import حل می‌شود ولی حداکثر `probable` است. نام نسبی در `import_module` نسبت
  به آرگومان `package=` حل می‌شود (مثل `importlib.util.resolve_name`)؛ level ی `__import__` فقط
  وقتی نسبت به ماژول import‌کننده حل می‌شود که `globals` همان فراخوانی ساده‌ی `globals()` باشد.
  `fromlist` دنبال نمی‌شود.
- نام محاسبه‌شده، فراخوانی با `*args` یا `**kwargs`، یا `package=` ی محاسبه‌شده `dynamic`
  (unknown) است.
- `exec` و `eval` (فقط وقتی همان builtin باشند) فایل را با `dynamic_construct_seen` علامت
  می‌زنند؛ مکانشان **ثبت نمی‌شود** (برایشان یالی وجود ندارد).

پشتیبانی نشده (ساختار اصلاً دیده نمی‌شود): assignment expression (`:=`) و نام‌هایی که
`from m import *` می‌آورد به‌عنوان انقیاد؛ alias ی alias؛ `getattr(importlib, "import_module")`؛
`__import__` ی رسیده از `globals()["__import__"]`؛ کد `eval` شده. جدول آگاه از scope ترتیب جست‌وجوی
پایتون را دنبال می‌کند (scope ی class داخل تابع تودرتو رد می‌شود) و نامی که در جایی `global`
اعلام شده در سطح ماژول مبهم است.

## ریشه‌های سورس و نام ماژول

نام ماژول از یک ریشه‌ی سورس شروع می‌شود. ریشه‌ی یک فایل به ترتیب این است:

1. ریشه‌ی اعلام‌شده در `pyproject.toml` که فایل را در بر بگیرد: maturin `python-source`؛
   setuptools `package-dir` (کلید خالی `{"" = "src"}` یعنی بدون پیشوند؛ کلید نام‌دار
   `{"mypkg" = "lib/other"}` می‌گوید پوشه‌ی `lib/other` **همان** بسته‌ی `mypkg` است، پس
   `lib/other/a.py` همان `mypkg.a` است)؛ setuptools `packages.find.where`. بلندترین پوشه‌ی
   اعلام‌شده برنده است؛
2. وگرنه نزدیک‌ترین پوشه‌ی بالادست بدون `__init__.py`.

ریشه‌ی اعلام‌شده باید مسیر نسبی داخل مخزن باشد: مسیر مطلق، backslash، درایو ویندوز، یا `..` ی
که از مخزن بیرون برود **رد** و در `meta.rejected_roots` فهرست می‌شود (هرگز بی‌صدا استفاده یا
حذف نمی‌شود)؛ `./src/` و `a/../b` نرمال می‌شوند.

نام ماژول فقط برای مسیری داخل ریشه‌اش ساخته می‌شود. `__init__.py` ی سطح ریشه نام قابل‌import
ندارد (با ماژول خالی فهرست می‌شود و importهایش با مسیر فایل گزارش می‌شود). پوشه‌ی بدون
`__init__.py` بسته‌ی **namespace** ضمنی است؛ بسته‌ی namespace می‌تواند در چند ریشه سهم داشته
باشد (PEP 420) و برای هر (نام، ریشه) یک `ModuleEntity` نگه داشته می‌شود؛ نامی که در هر ریشه
بسته‌ی عادی است همزمان namespace هم نیست. نامی که در دو ریشه هست فقط وقتی حل می‌شود که
ریشه‌ی خود import‌کننده دقیقاً یکی از آن‌ها را داشته باشد (`probable`)؛ وگرنه
`internal_unresolved` است.

راه‌اندازی بسته‌ی والد (`import a.b.c` ابتدا `a/__init__.py` را اجرا می‌کند) به‌عنوان یال
**مدل نمی‌شود**: هر بسته و زیرماژول‌هایش را چرخه می‌کرد. `from pkg import name` فقط وقتی به
`pkg` وابسته است که `name` زیرماژول مخزن نباشد.

**مسیرهای داده‌شده به builder** (`included`، `skipped`) نسبی و داخل پروژه و بدون `..` هستند؛
مسیر مطلق یا خروج با parent باعث `ValueError` می‌شود.

## چرخه‌ها

مؤلفه‌های قویاً همبند گراف import مخزن، بدون بازگشت، به‌اضافه‌ی ماژولی که خودش را
import می‌کند. فقط یال‌هایی حساب می‌شوند که به ماژول مخزن با اعتماد `definite` یا
`probable` حل شده باشند.

`Cycle.edges` **همه‌ی** چنین یال‌هایی است که دو سرشان در چرخه است، از جمله یال‌های lazy و
type-only، هرکدام با پرچم خودش. مجموعه‌ی کمینه‌ی یال‌هایی که یک حلقه را می‌بندند نیست. چرخه
**eager** است وقتی پس از حذف یال‌های `type_only` و `lazy` هنوز بماند، یعنی بتواند هنگام import
شکست بخورد؛ یال‌های `conditional` هنوز eager حساب می‌شوند (روی بعضی مسیرها اجرا می‌شوند).
وگرنه «lazy or type-only» فهرست می‌شود.

## قرارداد مدل

- **دو نسخه‌ی شما.** شمای **گزارش** بیرونی (`schema_version`، `"1.11"`) همراه گزارش JSON نسخه
  می‌شود (`docs/JSON_SCHEMA.fa.md`). شمای **مدل ساختار** همان `structure.schema` است، یک عدد
  صحیح، امروز `4` (`1` فقط importها بود، `2` نمادها و روابط و نقاط ورود را اضافه کرد، `3` فیلد `fingerprint` نماد و
  `meta.fingerprint_basis` را اضافه کرد، `4` باعث شد `declared_in` نام بخش manifest را بگوید و روش حل
  `declared-distribution` اضافه شد). این دو مستقل تغییر می‌کنند.
- **مختصات.** `line` از ۱ شروع می‌شود (۰ = نامعلوم). `col` و `end_col` **offset بایتی UTF-8**
  از ۰ در همان خط‌اند، دقیقاً همان‌طور که `ast` می‌دهد (`end_col` برابر ۰ = نامعلوم).
  `SyntaxError` کاراکتر گزارش می‌کند؛ سرند آن را به بایت تبدیل می‌کند تا کل مدل یک واحد داشته
  باشد. form feed شماره‌ی خط را جابه‌جا نمی‌کند (خط با `\n`، `\r\n` یا `\r` تمام می‌شود، مثل
  tokenizer پایتون).
- **اعتبارسنجی.** هر موجودیت هنگام ساخته‌شدن فیلدهایش را بررسی می‌کند: مقداری بیرون از
  واژگان بسته، مسیر نادرست (مطلق، backslash، `..`) یا مختصات منفی `ModelError` می‌دهد که نام
  فیلد و مقدارهای مجاز را می‌گوید. پس داده‌ی نامعتبر به خلاصه یا رندر نمی‌رسد.
- **تغییرناپذیری.** عمیق: mappingهای تودرتو فقط‌خواندنی‌اند و دنباله‌ها tuple؛ ساختن
  موجودیت چیزی را که می‌گیرد کپی می‌کند.
- **نامعلوم نامعلوم می‌ماند.** فایلی که خوانده نشد `size: null`، `sha256` خالی و محدودیت
  `unreadable` دارد؛ هرگز مثل فایل خالی نشان داده نمی‌شود.
- **شاهد** متن خود دستور است، از ستون شروع تا ستون پایانش (کامنت انتهایی جزو آن نیست)،
  خط‌هایش با فاصله‌ی تکی چسبیده و در ۲۴۰ کاراکتر بریده می‌شود (برش با `...` تمام می‌شود).
  `note` متن خود سرند برای توضیح یال حل‌نشده یا پویا است؛ هرگز متن سورس نیست.
- **خروجی کانونی.** serializer هر مجموعه را با کلید صریح مرتب می‌کند (فایل‌ها با مسیر؛
  ماژول‌ها با نام، ریشه، مسیر؛ بیرونی‌ها با نام؛ یال‌ها با مبدأ، مکان، نام درخواستی و بقیه؛
  چرخه‌ها با ماژول‌هایشان؛ یال‌های چرخه مثل یال‌ها)، mappingها را بازگشتی با کلید مرتب
  می‌کند و دنباله‌های `meta` را مرتب می‌کند. دنباله‌های داخل `extensions` ی فایل ترتیبشان
  را نگه می‌دارند. پس دو مدل برابر، با هر ترتیبی که سازنده‌ها داشتند، همان بایت‌ها را
  می‌دهند و serialize کردن مدل را تغییر نمی‌دهد.

## منشأ تجزیه و محدودیت‌ها

هر فایل منشأ دارد: parser (`python-ast`)، نسخه‌ی مفسر، کامل‌بودن (`full`، `partial`،
`failed`، `skipped_size`) و کدهای محدودیت: `syntax_error`، `encoding_error`، `recursion_limit`،
`resource_limit`، `node_cap`، `too_large`، `unreadable`، `dynamic_construct_seen`؛
`unsupported_syntax_for_interpreter` تعریف شده ولی **تولید نمی‌شود**: خطای نحوی را نمی‌شود
به‌طور قابل‌اعتماد به دستور زبان جدیدتر نسبت داد، پس فقط `syntax_error` گزارش می‌شود. فایلی
که خوانده نشود با دلیل و مکان خطا در خروجی می‌ماند، پس فایل خراب هرگز صفر بی‌صدا نیست.

محافظ‌ها: شکست بازگشت هنگام پیمایش فقط همان دستور را از دست می‌دهد (فایل `partial` است و
بقیه‌ی importها می‌مانند)؛ سقف گره (۱٬۰۰۰٬۰۰۰) و شکست حافظه پیمایش را متوقف می‌کنند
(`partial`، با آنچه پیش از آن پیدا شده)؛ شکست بازگشت یا حافظه هنگام parse فایل را `failed`
می‌کند. فقط همین شکست‌ها مدیریت می‌شوند؛ هر چیز دیگر باگ است و بلعیده نمی‌شود.

**«شناسایی نشد» یعنی «وجود ندارد» نیست.** importهای پویا، `getattr`/`setattr`،
monkey-patching، بارگذاری پلاگین با entry-point و کد تولیدشده می‌توانند رابطه‌هایی بسازند
که خواندن ایستا نمی‌بیند. `dynamic_construct_seen` یعنی فایل چنین ساختاری دارد.

دو ورودی محیطی در `meta` نام برده می‌شوند و پنهان نیستند: نسخه‌ی مفسر (دستور زبان `ast`
و فهرست stdlib به آن بستگی دارند، پس فایل با نحو جدیدتر روی مفسر قدیمی‌تر `failed` است) و
منبع فهرست stdlib.

## نمادها، روابط و نقاط ورود (R14-A2)

`--structure` حالا **نمادهایی** را که سورس تعریف می‌کند و **روابط** بینشان را هم فهرست می‌کند.
همه چیز از `ast` خوانده می‌شود؛ چیزی اجرا نمی‌شود و **هیچ نوعی استنتاج نمی‌شود**: هر استفاده فقط با
انقیاد نام درون مخزن حل می‌شود (scope لغوی، import، بدنه‌ی کلاس و کلاس‌های پایه).

### نمادها

انواع: `class`، `function`، `method`، `property`، `variable`، `constant` (انتساب سطح ماژول یا کلاس
با نام `UPPER_CASE`). صفت‌های نمونه (`self.x = ...`) و متغیرهای محلی نماد نیستند. هر نماد یک `id`
دارد (`sym:` و ۱۲ رقم hex از زبان، نوع، مسیر، نام کامل و `#n` برای تکراری)، `qualname`
(`Outer.method` و `outer.<locals>.inner`)، `module`، `path`، `parent` (کلاس یا تابع دربرگیرنده؛
در سطح ماژول خالی: همان رابطه‌ی `defines` طرح که یک بار ذخیره می‌شود)، `location`، `decorators` و
`bases` به همان متن نوشته‌شده و به ترتیب سورس، `flags` (`nested`، `conditional`، `dynamic`) و
`extensions` و `fingerprint` (بخش «شناسه و بصمت»). property از روی دکوراتور نوشته‌شده شناخته می‌شود و accessorهای یک property یک انقیادند.
stubهای `@overload` نماد هستند اما نام را مقید نمی‌کنند. `id` شماره‌ی خط ندارد، پس با قالب‌بندی و
ویرایش نامرتبط ثابت می‌ماند.

### روابط

انواع: `calls`، `inherits`، `references` (نام یا صفتِ به‌کاررفته ولی فراخوانی‌نشده، دکوراتور، annotation).
هر رابطه منبع (نماد، یا ماژول برای کد سطح ماژول)، هدف (نماد، ماژول، `unresolved` یا `dynamic`)،
`confidence`، `resolution_method`، `evidence`، `location`، `flags` (`conditional`، `type_only`، `lazy`،
`annotation`) و `note` دارد. روابط یکسان **ادغام** می‌شوند: `count` تعداد محل‌هاست و `location` و
`evidence` از اولین محل است. `depends_on` ذخیره نمی‌شود: در R14-B از روابط و importها مشتق می‌شود.

### قواعد اعتماد

پایین‌ترین سطح مسیر حاکم است. شرطی‌بودن پرچم است، نه سطح.

| سطح | قاعده |
|---|---|
| `definite` | نامی که در ماژولش یک بار با `def`/`class` تعریف شده؛ `from m import f` وقتی `m` یک بار `f` را تعریف می‌کند (از زنجیره‌ی re-export تا عمق ۸ هم)؛ `mod.f` از راه `import mod`؛ `Cls.member` وقتی همان کلاس عضو را یک بار تعریف می‌کند؛ کلاس پایه‌ای که با یکی از این‌ها مقید است |
| `probable` | `self.m()` و `cls.m()` (زیرکلاس ممکن است override کند)؛ عضوی که در کلاس پایه پیدا شود (پیمایش depth-first است، نه MRO دقیق)؛ `super().m()`؛ نامی از `from m import *` وقتی `m` یک `__all__` ایستا دارد؛ تعریفی که دکوراتورش در جدول دکوراتورهای شفاف نیست؛ alias (`Foo = Bar`)؛ صفت ماژول یا کلاسی که جایی انتسابش می‌دهند (`mod.f = g` و `setattr(mod, "f", g)`)؛ نامی که هم صفت است و هم زیرماژول؛ `cls()` |
| `unknown` | `getattr`/`setattr`/`delattr` با نامی که ثابت رشته‌ای نیست؛ star import که منبعش `__all__` ایستا ندارد (یا دو منبع نام را فهرست می‌کنند)؛ `__getattr__` سطح ماژول؛ دو انقیاد برای یک نام (از جمله بازانتساب با `global`)؛ کلاس پایه‌ی حل‌نشده؛ `__getattr__` کلاس؛ نامی که ماژول تعریف نمی‌کند |

`self.m()` عمداً هرگز `definite` نمی‌شود: نمونه ممکن است به زیرکلاسی بیرون مخزن تعلق داشته باشد.

### چه ذخیره می‌شود و چه شمرده می‌شود

یک محل استفاده فقط وقتی به‌صورت رابطه **ذخیره** می‌شود که به مخزن حل شود (با هر اعتمادی) یا یکی از
شکل‌های مشخص `unknown` بالا باشد. هر محل دیگر **شمرده** می‌شود و هرگز بی‌صدا حذف نمی‌شود:
`structure.sites` مقدار `total` و فرجام هر محل را دارد: `internal`، `external_stdlib`،
`external_declared`، `external_unmatched`، `builtin`، `unresolved`، `dynamic`، `untracked` (با
`untracked_by_reason`). دلایل فهرستی بسته‌اند: `local_binding`، `expression_without_a_name`،
`instance_attribute`، `attribute_of_value`، `call_of_variable`، `call_of_module`، `base_not_a_class`،
`unbound_name`، `attribute_by_constant_name`، `self_reference`، `module_not_analysed`،
`reexport_depth`، `ambiguous_binding_without_repository_candidate`. خواندن متغیر محلی، نام خالی ماژول
یا `self` خالی محل استفاده نیست و شمرده نمی‌شود. استفاده از چیزهای بیرون مخزن در `external_use`
جمع می‌شود. `sites.total == internal + external_* + builtin + unresolved + dynamic + untracked`.

### نقاط ورود

هرکدام `type`، `name`، `target`، `resolved`، `confidence`، `method`، `evidence` و `note` دارد:
`main_block` (`if __name__ == "__main__":` سطح ماژول، definite)، `package_main` (فایل `__main__.py`،
definite)، `console_script` (`[project.scripts]`، `[project.gui-scripts]`، `[tool.poetry.scripts]`) و
`entry_point_group` (`[project.entry-points.<group>]`): هدف `module:attr` با اعتماد همان حل به نماد
می‌رسد یا با یادداشت `unknown` می‌ماند؛ `test_root` (`testpaths` در `[tool.pytest.ini_options]`؛
وقتی فایلی زیر آن باشد definite)؛ `framework_app` (فقط probable: `click.command`/`click.group` با
اعلام `click`، `typer.Typer()` با اعلام `typer`، `argparse.ArgumentParser()`). تابع ساده هرگز نقطه‌ی
ورود نیست. فهرست entry pointهای Quick Context تغییری نکرده است.

### حدها (تشخیص‌داده‌نشده یعنی نبودنش ثابت نشده)

annotationهای رشته‌ای و forward reference خوانده نمی‌شوند. `:=` هنگام رسیدن پیمایش مقید می‌کند.
صفت نمونه، صفت مقدار با نوع ناشناخته، descriptor، رفتار ساخته‌شده با metaclass و دکوراتور، تزریق
با registry یا entry-point group (sarand افزونه‌های تحلیلگر خودش را این‌گونه بار می‌کند)،
`exec`/`eval`، تغییر `globals()` و `__init_subclass__` دنبال نمی‌شوند؛ جایی که فایل چنین ساختاری
را نشان دهد محدودیت `dynamic_construct_seen` را دارد. اگر پیمایش نماد به سقف گره، بازگشت یا حافظه
برسد، آنچه خوانده نگه داشته می‌شود و فایل `partial` می‌شود. `implements` و `overrides` در پایتون
وجود ندارند و تولید نمی‌شوند.

## شناسه و بصمت (R14-A3)

مقایسه‌ی بعدی دو اجرا (baseline، R14-D) باید بداند کدام نماد حالت جدید همان کدام نماد حالت قدیمی است.
R14-A شناسه را تعریف و آزمایش می‌کند؛ هنوز اجراها را مقایسه نمی‌کند.

- **`id` نماد** همان شناسه است: `sym:` و ۱۲ رقم hex از زبان، نوع، مسیر نسبی مخزن، نام کامل و `#n` برای نام
  تکراری. شماره‌ی خط و محتوا ندارد، پس با قالب‌بندی، کامنت، docstring و ویرایش نامرتبط ثابت می‌ماند و با
  تغییر نام نماد یا جابه‌جایی فایل عوض می‌شود.
- **`fingerprint`** (`fp1:` و ۱۲ رقم hex) به پرسش دیگری جواب می‌دهد: *آیا محتوای این تعریف عوض شده؟*
  SHA-256 روی پیمایش استانداردشده‌ی درخت نحوی تعریف است. موقعیت، فاصله‌گذاری، پرانتز، نوع quote، ویرگول
  پایانی، کامنت و docstring تابع یا کلاس را نادیده می‌گیرد و هر دستور و عبارت، تعریف‌های تودرتو،
  دکوراتور، مقدار پیش‌فرض و annotation را شامل می‌شود. پس بصمت کلاس متدهایش را هم دربرمی‌گیرد. بصمت
  متغیر فقط از annotation و مقدارش ساخته می‌شود تا هدف دیگرِ همان دستور آن را عوض نکند. الگوریتم در
  `structure/fingerprint.py` است و هر تغییرش `fp1` را بالا می‌برد.
- **پایه** (`meta.fingerprint_basis`، مثلاً `fp1/python-3.12`) نسخه‌ی الگوریتم و نسخه‌ی minor مفسر را
  نام می‌برد، چون درخت نحوی بین نسخه‌های پایتون فرق دارد. بصمت‌ها فقط بین خروجی‌هایی با پایه‌ی یکسان
  مقایسه می‌شوند؛ بین پایه‌های مختلف فقط `id` تطبیق می‌خورد.
- **کلاس‌های تطبیق** (`structure/identity.py`، `match_symbols`) بین فهرست قدیم و جدید نمادها. هر نماد
  دقیقاً در یک ردیف می‌آید و نتیجه به ترتیب ورودی بستگی ندارد.

| کلاس | معنی |
|---|---|
| `exact` | همان `id` و بدون ابهام؛ `content_changed` می‌گوید بصمت فرق کرده یا نه (`null` اگر مقایسه ممکن نباشد) |
| `probable` | همان نوع، نام کامل و بصمت در مسیر دیگر (جابه‌جایی)، با دقیقاً یک نامزد در هر طرف |
| `ambiguous` | چند نامزد دست‌کم در یک طرف: نام کامل تکراری که با محتوا جفت نمی‌شود یا چند نامزد جابه‌جایی به‌یک‌اندازه خوب؛ همه‌ی نامزدها فهرست می‌شوند و هیچ‌کدام انتخاب نمی‌شود |
| `unmatched` | در طرف دیگر چیزی نیست (`removed` یا `added`)؛ تغییر نام نماد عمداً یک جفت unmatched است چون R14-A تغییر نام را حدس نمی‌زند |

حدها: بصمت هش امنیتی نیست و هرگز تنها تصمیم نمی‌گیرد (فقط می‌تواند تطبیق را `probable` کند)؛ نمادی که هم
جابه‌جا شده و هم تغییر کرده همتا ندارد؛ متدی که با کلاسش جابه‌جا شده نماد‌به‌نماد تطبیق می‌خورد؛ دو
خروجی از نسخه‌های minor متفاوت پایتون فقط با `id` تطبیق می‌خورند. تطبیق روی نمادها تعریف شده؛ روابط و
نقاط ورود هنوز تطبیق داده نمی‌شوند.

## ارزیابی روی مخزن‌های واقعی

`scripts/structure_eval.py` زمان و حافظه را اندازه می‌گیرد، تکرارپذیری بایتی را می‌سنجد و نمونه‌های
بازبینی دستی با seed ثابت می‌کشد (۵۰ رابطه‌ی `Definite`، ۵۰ `Probable`، ۵۰ `Unknown` و ۵۰ جای استفاده‌ی
شمرده‌شده ولی ذخیره‌نشده). نتیجه برای sarand و click، قاعده‌ی قضاوت هر ردیف و خود ردیف‌های بازبینی‌شده در
`docs/R14A_GATE_REPORT.md` و `docs/eval/` است. اعداد **برآورد از نمونه‌های کوچک‌اند**، نه دقت.

## کجا دیده می‌شود

- **JSON** (`structure`، شمای بیرونی ۱٫۱۰، شمای ساختار ۴): همه‌چیز، از جمله هر یال با شاهد، note و مکانش. به
  `docs/JSON_SCHEMA.fa.md` نگاه کنید.
- **Markdown و HTML**: شمارش‌ها؛ چرخه‌های import (۱۰ مورد اول)؛ **importهای حل‌نشده و پویا**
  (۲۰ مورد اول): importهایی که کلاس هدفشان `internal_unresolved` یا `dynamic` است، با دلیل؛
  و **بسته‌های بیرونی import‌شده** (۳۰ مورد اول، از نوع `external_declared` و
  `external_unmatched`، با اینکه چند ماژول هرکدام را import می‌کنند). جمع کل همیشه نشان داده
  می‌شود و فهرست بریده می‌گوید چند مورد نشان داده نشده. بخش خالی رسم نمی‌شود. هر سلول
  escape می‌شود (موجودیت HTML در HTML؛ pipe و شکست خط در جدول Markdown).
- **Text**: یک خط.
- **SARIF**: شامل نمی‌شود.

همه‌ی شمارش‌ها از یک جا می‌آیند (`structure/serialize.py` و `core/report_views.py`)، پس
قالب‌ها هم‌نظرند.

## هنوز پیاده‌سازی نشده

مقایسه‌ی دو اجرا (baseline، R14-D)، تطبیق روابط و نقاط ورود، و زبان‌های دیگر. حدهای دقتی که ارزیابی پیدا
کرد: متدی که روی متغیر محلی یا پارامتری فراخوانی می‌شود که کلاسش فقط از ساختن شیء یا annotation معلوم است
حل نمی‌شود (استنتاج نوع محلی نداریم)، و کلاسی که `__getattr__` دارد هر صفتِ پیدانشده در اعضای کلاس را
`unknown` می‌کند، حتی صفت نمونه‌ای که خود کلاس مقدار می‌دهد. ساختارهای import پایتون که هنوز پشتیبانی
نمی‌شوند زیر «شکل‌های شناخته‌شده و حدشان» فهرست شده‌اند.

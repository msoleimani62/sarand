# نوشتن پلاگین برای sarand

پلاگین به sarand یاد می‌دهد یک زبان یا ابزار دیگر را هم بشناسد. پلاگین یک
بسته‌ی معمولی پایتون است که یک کلاس را زیر گروه entry-point به نام
`sarand.analyzers` ثبت می‌کند. sarand آن را پیدا می‌کند، طوری می‌پیچد که
نتواند اسکن را از کار بیندازد و کنار آنالایزرهای داخلی اجرا می‌کند.

[English](PLUGINS.md) · یک نمونه‌ی کامل و کارا در
[`examples/sarand-plugin-justfile`](../examples/sarand-plugin-justfile) است.

## قرارداد

`PLUGIN_API_VERSION` برابر **۱** است. کلاس شما باید این‌ها را داشته باشد:

| عضو | اجباری | معنی |
|---|---|---|
| `name: str` | بله | نام نمایشیِ غیرخالی و یکتا، مثل `"Zig"`. |
| `matches(root)` | بله | وقتی ابزار شما به پروژه می‌خورد `True`. فقط فایل نشانگر واقعی را بررسی کنید؛ اینجا هیچ ابزاری اجرا نکنید. |
| `entry_points(root)` | بله | فایل‌های نقطه‌ی ورودِ موجود زیر `root` (می‌تواند خالی باشد). |
| `async run_tests(root)` | بله | مجموعه‌ی تست را اجرا کنید یا اگر چیزی نیست `None` برگردانید. |
| `async run_quality(root)` | بله | بررسی lint و format؛ در غیر این صورت فهرست خالی. |
| `async run_security(root)` | نه | بررسی وابستگی و آسیب‌پذیری؛ اگر ندارید حذفش کنید. |
| `api_version: int` | نه | نسخه‌ی API پلاگین که برایش نوشته شده‌اید؛ پیش‌فرض ۱. |

قواعدی که پلاگین را خوش‌رفتار نگه می‌دارند:

- sarand متدهای `run_*` را فقط وقتی صدا می‌زند که `matches(root)` برابر `True` بوده باشد.
- اگر ابزار خارجی نصب نیست، نتیجه‌ی *skipped* برگردانید
  (`make_command_result(kind, 127, "", 0.0, skipped=True, skip_reason="x not found in PATH")`)،
  نه شکست. نبودن ابزار یک اطلاع است، نه خرابی پروژه.
- همه‌ی متدهای `run_*` از نوع `async` هستند و ممکن است همزمان با آنالایزرهای
  دیگر اجرا شوند. برای زیرفرایندها از `run_cmd_async` استفاده کنید: timeout دارد و
  گروه فرایند را پاک‌سازی می‌کند.
- داخل پوشه‌ی پروژه چیزی ننویسید.

### سطح عمومی

فقط این‌ها را از sarand import کنید؛ بقیه ممکن است بی‌اطلاع تغییر کنند:

- `sarand.analyzers.base.LanguageAnalyzer` و `PLUGIN_API_VERSION`
- `sarand.models.results.CommandResult` و `Issue`
- `sarand.utils.command.make_command_result` و `run_cmd_async`

## sarand برای شما (و روی شما) چه می‌کند

**چرخه‌ی عمر.** در هر اسکن یک نمونه با `YourClass()` (بدون آرگومان) ساخته می‌شود،
متدها صدا زده می‌شوند و نمونه دور انداخته می‌شود. `__init__` را سبک نگه دارید و
بین اسکن‌ها حالتی نگه ندارید.

**جداسازی خطا.** هر پلاگین پیچیده می‌شود. اگر استثنا بدهد، نوع بازگشتی نادرست
برگرداند یا عضو نامعتبر در فهرست بدهد، sarand یک هشدار ثبت می‌کند و یک نتیجه‌ی
skipped با نام پلاگین، فاز و خطا جایگزین می‌کند. اسکن و همه‌ی آنالایزرهای دیگر ادامه
می‌دهند. خرابی پلاگین هرگز شکستِ تستِ پروژه‌ی کاربر حساب نمی‌شود. پلاگینی که import
یا ساخته نشود با هشدار رد می‌شود.

**پلاگین ردشده.** پلاگین بدون `name` قابل‌استفاده، بدون یکی از متدهای اجباری، یا با
`api_version` بزرگ‌تر از آنچه sarand پشتیبانی می‌کند، با ثبت دلیل رد می‌شود.

**نام تکراری.** اگر `name` شما با یک آنالایزر داخلی یا پلاگین قبلی یکی باشد (بدون
حساسیت به حروف)، پلاگین شما رد می‌شود. اولی برنده است؛ نام متفاوت انتخاب کنید.

**ترتیب.** پلاگین‌ها به ترتیب نام entry-point بارگذاری می‌شوند تا نتیجه تکرارپذیر باشد.

ارائه نمی‌شود: sandbox و timeout برای کاری که زیرفرایند نیست. پلاگینی که برای همیشه
منتظر چیزی بماند اسکن را قفل می‌کند.

## سازگاری نسخه

`PLUGIN_API_VERSION` فقط وقتی عوض می‌شود که قرارداد طوری تغییر کند که پلاگین‌های
قدیمی تحملش نکنند. افزودن عضو اختیاری (مثل `run_security`) نسخه را بالا نمی‌برد.

- پلاگین بدون `api_version` نسخه‌ی ۱ حساب می‌شود.
- پلاگینی که نسخه‌ی **بالاتر** از پشتیبانیِ sarand اعلام کند رد می‌شود و به کاربر
  گفته می‌شود sarand یا پلاگین را ارتقا دهد.
- پلاگینِ نسخه‌ی پایین‌تر تا وقتی sarand آن نسخه را پشتیبانی کند کار می‌کند؛ حذف‌ها
  قبلاً در changelog اعلام می‌شوند.
- در `pyproject.toml` کران پایین sarand را بگذارید (`dependencies = ["sarand>=0.6.11"]`).

## روند کار نویسنده

۱. **از نمونه شروع کنید.** `examples/sarand-plugin-justfile` را کپی کنید و نام بسته،
   کلاس و کلید entry-point را عوض کنید.
۲. **قرارداد بالا را پیاده کنید.** `matches` باید سریع و بدون اثر جانبی باشد.
۳. **در `pyproject.toml` ثبتش کنید:**

   ```toml
   [project.entry-points."sarand.analyzers"]
   zig = "my_zig_plugin:ZigAnalyzer"
   ```

۴. **در همان محیطی نصب کنید که sarand از آن اجرا می‌شود.** اگر sarand را با pipx
   نصب کرده‌اید:

   ```bash
   pipx inject sarand ./my-plugin
   ```

   در virtualenv ساده در همان محیط `pip install ./my-plugin`. پلاگینی که در محیط
   دیگری نصب شود دیده نمی‌شود.
۵. **بررسی کنید پیدا می‌شود.** با Python داخل محیط sarand:

   ```bash
   python -c "from sarand.analyzers.registry import discover_analyzers; print([a.name for a in discover_analyzers()])"
   ```

   یا `sarand --verbose` را روی هر پروژه بزنید: برای هر پلاگینِ پذیرفته‌شده
   `Loaded plugin analyzer: ...` می‌نویسد. پلاگین ردشده همیشه، حتی بدون `--verbose`،
   با دلیل به‌صورت هشدار ثبت می‌شود.
۶. **مثل هر بسته‌ای تستش کنید.** `asyncio.run(YourAnalyzer().run_tests(path))` روی
   یک پوشه‌ی موقت برای بیشتر پلاگین‌ها کافی است.
۷. **sarand را روی یک پروژه‌ی واقعی** با فایل نشانگر شما اجرا کنید و نتایج را با
   رشته‌های `kind` خودتان پیدا کنید.

عمداً هیچ registry یا بازارچه‌ای برای پلاگین ساخته نشده: اول API باید پایدار شود.

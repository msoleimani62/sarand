# شواهد امنیتی

وقتی یک ابزار امنیتی با کد غیرصفر تمام می‌شود، می‌تواند چهار چیز متفاوت باشد.
سرند آن‌ها را از هم جدا نگه می‌دارد، چون گزارشی که این‌ها را قاطی کند چیزی به
خواننده می‌گوید که شواهد پشتوانه‌اش نیستند.

| چه شد | سرند چه گزارش می‌کند | آسیب‌پذیری است؟ |
|---|---|---|
| ابزار اجرا نشد (timeout، نصب نبودن، خطای سیستم‌عامل) | یک شکاف در execution coverage و پیشنهاد اجرای دوباره | نه: چک حکمی نداده |
| ابزار یک advisory گزارش کرد | «یافته‌ی امنیتی» و یک ورودی برای هر advisory در `advisories` | نتیجه‌ی ابزار؛ applicability بررسی نشده |
| یک وابستگی سیاست تنظیم‌شده را نقض می‌کند (cargo deny: لایسنس، ban، منبع) | «نقض سیاست وابستگی» | نه |
| ابزار شکست خورد و یافته‌ی شناخته‌شده‌ای چاپ نکرد | «شکست بدون یافته‌ی شناخته‌شده» | نه شاهدی به سود یا زیان |

سرند هرگز **آسیب‌پذیری تأییدشده در سطح برنامه** گزارش نمی‌کند: برای آن شاهد
مشخص از سوءاستفاده‌پذیری لازم است و کد خروج ابزار شاهد نیست.

## یک ورودی advisory چه دارد

هر ورودی در کلید JSON با نام `advisories`، در نتایج SARIF و در بخش Markdown با
عنوان «Dependency advisories» این واقعیت‌ها را دارد، همه از خروجی ابزار خوانده‌شده:

- `id`، `package`، `version`: مثلاً `RUSTSEC-2026-0385`، `ctutils`، `0.4.2`.
- `kind`: واژه‌ی پایگاه advisory: `vulnerability`، `unsound`، `unmaintained`،
  `yanked` یا `notice`.
- `title` و `url`.
- `fixed_versions`: نسخه‌هایی که ابزار نام می‌برد؛ وقتی ارتقای امنی نیست خالی.
- `severity`: مقدار upstream وقتی ابزار چاپ کرده، **`null` وقتی چاپ نکرده**.
  خروجی متنی RustSec فقط برای advisoryهای دارای امتیاز CVSS شدت چاپ می‌کند؛ پس
  نبودن مقدار رایج است و هرگز با حدس پر نمی‌شود.
- `sources`: همه‌ی چک‌هایی که آن را گزارش کرده‌اند. cargo audit و cargo deny یک
  advisory را یک بار می‌دهند.
- `database`: پایگاه advisory و تعداد advisoryهایی که ابزار بارگذاری کرده. ادعا
  نمی‌کند پایگاه به‌روز شده است.
- `applicability`: **برای همه‌ی ورودی‌ها `unknown`.**

## شدت و applicability دو واقعیت جدا هستند

یک advisory می‌تواند شدت upstream بالا داشته باشد در حالی که کسی نمی‌داند این پروژه
به کد آسیب‌دیده می‌رسد یا نه. سرند هر دو را نشان می‌دهد و applicability ناشناخته را
هرگز به شدت پایین تبدیل نمی‌کند، و شدت بالا را هم به ادعای سوءاستفاده‌پذیری.

تعیین applicability شواهدی می‌خواهد که سرند جمع نمی‌کند: پروژه کدام API وابستگی را
صدا می‌زند، کدام featureهای Cargo فعال است و کدام پلتفرم‌های هدف پشتیبانی می‌شوند
(advisory درباره‌ی allocator در WebAssembly به ساخت فقط-بومی ربطی ندارد، و advisory
درباره‌ی یک decoder به decoder دیگر). وجود یک crate در `Cargo.lock` هیچ‌کدام را
ثابت نمی‌کند. تا وقتی این شواهد جمع نشده مقدار `unknown` می‌ماند.

## اثر روی امتیاز سلامت

وزن‌های امنیت تغییر نکرده‌اند: ۱۵ امتیاز وقتی هر چک امنیتیِ اجراشده موفق باشد، ۵
وقتی یکی با حکم شکست خورده، ۸ وقتی هیچ‌کدام نتوانسته اجرا شود.

- چکی که runner نتوانست اجرا کند دیگر شکست نیست. قبلاً timeout یا نبودن باینری
  «Security tool reported issues.» حساب می‌شد و ۱۰ امتیاز کم می‌کرد.
- پیام critical حالا می‌گوید ابزار چه گزارش کرده: «Security finding reported by
  cargo audit (a tool result; exploitability is not assessed)»، یا «Dependency
  policy violation reported by cargo deny check (licenses, bans or sources); not a
  vulnerability»، یا «Security tool X failed without a recognised finding».
- ریسک `SEC-CHECK-FAILED` چکی را که نتوانسته اجرا شود نادیده می‌گیرد.

چکی که اجرا نشده همچنان دیده می‌شود: execution coverage آن را شکاف می‌نامد و یک
پیشنهاد می‌گوید چرا حکمی نداده.

## این کار چه چیزی را انجام نمی‌دهد

- **تحلیل reachability نیست.** applicability همان `unknown` می‌ماند.
- **refresh نیست.** سرند فقط آنچه cargo audit و cargo deny چاپ کرده‌اند را می‌خواند؛
  پایگاه advisory را نمی‌گیرد و advisory را با نسخه‌ی جدیدتر مقایسه نمی‌کند.
- **ابزارها مثل قبل اجرا می‌شوند.** خروجی متنی پارس می‌شود؛ حالت JSON اضافه نشده.
- **فقط cargo audit و cargo deny.** `pip-audit`، `npm audit` و بقیه‌ی ابزارهای
  امنیتی همچنان یک شکست طبقه‌بندی‌شده می‌دهند، نه ورودی advisory.
- **گزارش HTML و متنی** هنوز advisoryها را فهرست نمی‌کنند؛ Markdown، JSON و SARIF
  می‌کنند.

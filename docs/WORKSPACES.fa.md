# مخزن‌های چندبسته‌ای (monorepo) و workspace

sarand دو نوع مخزن چندبسته‌ای را می‌شناسد.

| مدل | روش تشخیص | کاری که sarand می‌کند |
|---|---|---|
| **workspace کارگو** | `[workspace]` در `Cargo.toml` ریشه | اعضا را فهرست می‌کند. `cargo test --all` خودش همه‌ی crateها را پوشش می‌دهد. |
| **workspace مربوط به npm / Yarn / pnpm** | کلید `"workspaces"` در `package.json` ریشه (آرایه، یا `{"packages": [...]}` در Yarn) یا فایل `pnpm-workspace.yaml` | اعضا را فهرست می‌کند و تست و lint را **داخل هر عضو** اجرا می‌کند. |

گزارش یک بخش **Workspace** (نوع و اعضا) می‌گیرد و در JSON کلید `workspace`.
مخزنی که **هر دو** workspace (کارگو و Node) را دارد برای هر کدام یک بخش
می‌گیرد (`## Workspace (cargo)` و `## Workspace (npm)`) و در JSON یک فهرست
`workspaces` کنار کلید بدون‌تغییر `workspace` (که همان عضو اول است).
نتیجه‌ی هر عضو با مسیرش برچسب می‌خورد، مثلاً `packages/api: npm test`، تا با
نتیجه‌ی ریشه قاطی نشود.

## اجرای workspaceهای Node

`npm test` در ریشه فقط اسکریپت `test` **خودِ ریشه** را اجرا می‌کند و به بسته‌ها
نمی‌رسد. پس sarand آنالایزر Node.js را داخل پوشه‌ی هر عضو اجرا می‌کند (`npm test`
وقتی عضو اسکریپت `test` دارد، و `npm run lint` و `eslint` وقتی تنظیم شده باشند).
اعضا پشت‌سرهم و حداکثر **۲۰** عضو اجرا می‌شوند؛ اگر بیشتر بود، یک نتیجه‌ی skipped
تعداد حذف‌شده‌ها را می‌گوید. این در مخزنی که workspace کارگو هم دارد همین‌طور است:
اعضای Node به‌عنوان عضو اجرا می‌شوند (تست و lint، هرگز `npm audit`) و اعضای کارگو
را `cargo test --all` پوشش می‌دهد.

برای اینکه چیزی دوبار گزارش نشود، اگر ریشه خودش یک فاز را پوشش بدهد آن فاز برای
اعضا رد می‌شود:

- **تست:** اسکریپت `test` ریشه خودش پخش می‌شود (`--workspaces`، `-ws`،
  `pnpm -r` یا `--filter`، `yarn workspaces`، `turbo`، `nx`، `lerna`، `wireit`).
- **lint:** اسکریپت `lint` ریشه همین‌طور پخش می‌شود، **یا** ریشه کانفیگ ESLint دارد
  (`eslint .` در ریشه خودش بسته‌ها را هم می‌گردد).
- **امنیت:** هیچ‌وقت برای هر عضو اجرا نمی‌شود. `npm audit` ریشه همان یک lockfile
  workspace را می‌خواند.

عضوی که در یک پروژه‌ی ترکیبی هم «application» حساب می‌شود (مثلاً یک اپ React و یک
API با Express در یک workspace) برای هر آنالایزر فقط یک اجرا می‌گیرد. با
`SARAND_NO_COMPONENTS=1` اجرای اعضا و اجرای per-component هر دو خاموش می‌شوند.

## امتیاز سلامت و workspace

**یک امتیاز در سطح کل مخزن** وجود دارد؛ هنوز امتیاز جدا برای هر بسته نیست. نتیجه‌ی
اعضا به همان فهرست‌های نتیجه‌ی ریشه می‌رود و هر چک یک بار شمرده می‌شود. شکست تستِ
یک عضو نسبت مشترک تست‌ها را پایین می‌آورد و «One or more test suites failed» را به
فهرست بحرانی اضافه می‌کند، دقیقاً مثل شکست تستِ ریشه.

## آنچه پشتیبانی نمی‌شود

- **Gradle چندپروژه‌ای و Maven چندماژوله** به‌عنوان workspace تشخیص داده نمی‌شوند.
  build ریشه‌شان (`./gradlew test`، `mvn test`) از قبل همه‌ی ماژول‌ها را پوشش می‌دهد؛
  فقط نمای ساختار گزارش کم است.
- **Bazel، Nx و Turborepo** به‌عنوان مدل workspace. Bazel اصلاً آنالایزر ندارد. Nx و
  Turborepo روی یک workspace از نوع npm/Yarn/pnpm سوارند: آن workspace تشخیص داده
  می‌شود و اسکریپت ریشه‌ای که آن‌ها را صدا بزند پخش‌شونده شناخته می‌شود، ولی گراف
  taskهایشان خوانده نمی‌شود.
- **دستورهای مخصوص هر package manager.** اعضا در مخزن pnpm یا Yarn هم با `npm test`
  تست می‌شوند؛ اسکریپت‌ها اجرا می‌شوند، ولی مخزنی که از طریق corepack استفاده از `npm`
  را ممنوع کرده ابزار خودش را می‌خواهد.
- **رابطه‌ی بسته‌های عضو با هم** (کدام بسته به کدام وابسته است).

## بسته‌های تو در تو در پروژه‌ی ترکیبی

در پروژه‌ی ترکیبی (مثلاً ریشه‌ی Node با یک `web/` ری‌اکتی و یک `api/` اکسپرسی
پشت یک فایل compose)، بسته‌ی تو در توی Node.js، Go یا Rust هم تحلیل می‌شود، با اینکه
همان آنالایزر ریشه را هم match می‌کند، چون اجرای ریشه به آن نمی‌رسد: `npm test` از
مرز بسته رد نمی‌شود، `go test ./...` ماژول‌های تو در تو را رد می‌کند و
`cargo test --all` فقط اعضای workspace را می‌گیرد. اگر ریشه خودش آن را پوشش بدهد
دوباره تحلیل **نمی‌شود**: عضو workspace از نوع Node یا Cargo، یا هر چیزی در
مخزنی که `go.work` دارد. اسکریپت‌های تست و lint ریشه که خودشان پخش می‌شوند، یا کانفیگ
ESLint ریشه، همان فازها را دقیقاً مثل اعضای workspace حذف می‌کنند. Python به این قاعده
نیاز ندارد چون `pytest` و `ruff` ریشه خودشان زیرپوشه‌ها را می‌گردند. پروژه‌ای که
ترکیبی نیست (یک نوع بسته، بدون compose، Kubernetes یا Terraform) با همان قاعده
برنامه‌ریزی می‌شود: آنالایزری که ریشه را match نمی‌کند داخل هر بسته‌ی تو در تو اجرا
می‌شود و آنالایزری که match می‌کند تکرار نمی‌شود (جز آن سه).
